# MOY IQ (ex FinanceOS) — App

PWA de finanzas personales. React 18 + Vite + IndexedDB. **Privacy-first: los datos financieros viven en el dispositivo** y el servidor no los lee. Supabase (proyecto compartido con Invest) guarda cuentas (login obligatorio desde el 12-sep-2026), licencias y entitlements, leads/CRM y el estado de los correos de seguimiento; el sync de blobs *ya cifrados en el cliente* existe pero está apagado (ver "Auth compartido" y "Sync en la nube").

```bash
npm run dev      # vite
npm run build    # node build.js -> dist/index.html (redirect) + dist/app/ (la app real)
npm test         # vitest run — src/, api/, supabase/functions/ y scripts/ (ver "Testing")
```

**Variables locales en `.env.local`** (nunca en `.env`, que se retiró del repo el 20-oct-2026): `npm run dev` necesita `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` (nombres en `.env.example`; los valores de producción están en Vercel). Ningún script local usa claves de servidor. `.vercelignore` excluye `.env*` para que el CLI no las suba.

**El build produce dos cosas.** `dist/index.html` es solo un redirect a la landing; la app de verdad está en `dist/app/index.html`. Para verificar algo del `<head>` (fuentes, meta), mirar **`dist/app/index.html`**, no el de la raíz.

## Deploy

**Hay dos caminos a producción y los dos salen de `main`** (verificado con la API de Vercel el 19-oct-2026):

(Esta sección decía que un push no actualizaba el dominio: era falso, casi todos los deploys de producción del 18-oct fueron `source=git`.)
2. **`./deploy.sh`** (desde 2026-09-06; guard desde el 19-oct; dos dominios desde el 20-oct): guard (rama `main`, sin cambios rastreados sin commitear, igual a `origin/main`, ver "Sesiones paralelas y despliegue"), tests, build local (gate), `vercel deploy --prod` por CLI, los DOS alias y un smoke test de `curl` a `/app/` y a `fonts.css` en los dos dominios. Aborta si falla cualquier paso. Con el guard, el CLI y git publican el mismo commit.

El dominio anterior de FinanceOS (app./demo.) **se desconectó el 20-oct-2026** por decisión de Walter (sin redirección; quien tuviera datos solo locales en ese origen los pierde): no figura en `vercel.json`, `deploy.sh`, CORS ni código. No volver a agregarlo.

Manual, si hace falta un paso suelto:

```bash
npx vercel --prod --yes
```

Con la URL que devuelve, aliasear **los cuatro** dominios (`moyiq.app` es el primario desde 11-sep-2026):

```bash
npx vercel alias <url-nueva> app.moyiq.app
```

Y repetir con `demo.moyiq.app`. Si solo se aliasea uno, el otro se queda en la versión vieja.

El navegador integrado tiene bloqueado `*.moyiq.app` por política: verificar producción con `curl` por contenido, o en `localhost` con el servidor de desarrollo.

## Sesiones paralelas y despliegue

Varias sesiones de Claude trabajan este repo a la vez, y `vercel deploy` sube el árbol de trabajo tal como está. El 18-oct-2026 una sesión dejó el árbol en `security/cloudsync-encryption-guard` (sin mergear) y `./deploy.sh` publicó esa rama en producción (auditoría 360: OPS-5, GOB-5). Reglas:

1. **Trabajar en worktrees.** El árbol principal se queda siempre en `main`: nadie le cambia la rama. Todo cambio, y toda sesión que no sea la principal, va en un worktree propio: `git worktree add "/private/tmp/claude-501/moyiq-wt/financeos-app-<tema>" -b <fix|feat>/<tema> main`, con `node_modules` enlazado al del árbol principal (`ln -s`) salvo que el cambio toque `package.json`.
2. **Desplegar solo desde `main` limpio y con el candado.** Antes de integrar o desplegar: `mkdir /private/tmp/claude-501/moyiq-locks/financeos-app.lock` (atómico; si existe, esperar y reintentar hasta 20 min; si tiene más de 60 min es de una sesión caída y se toma). Al terminar: `rmdir` del mismo directorio. Secuencia: suite completa de tests → `git merge --ff-only` a `main` → `git push origin main` → `./deploy.sh` desde el árbol principal.
3. **`./deploy.sh` lo hace cumplir**, antes de cualquier paso: aborta si la rama no es `main`, si hay cambios rastreados sin commitear (los archivos no rastreados no cuentan) o si `HEAD` no coincide con `origin/main` tras `git fetch` (ni atrás ni adelante). `./deploy.sh --check` corre solo esa verificación, sin desplegar. Test del guard: `scripts/deployGuard.test.js` (corre con `npm test`).
4. **CI:** `.github/workflows/test.yml` corre `npm ci`, `npm run lint` (ESLint con `--max-warnings 0` desde el 21-oct-2026: un aviso nuevo rompe el CI; los `eslint-disable` llevan regla y motivo), `npm run typecheck`, `npm test` y `npm run build` en cada push y en cada PR a `main`. Proteger `main` (PR obligatorio con el check en verde) necesita permisos de dueño en GitHub: queda con Walter (W-27 de la auditoría).
5. **Edge Functions** (`supabase/functions/`, 19 funciones; `uptime-alert` y `cron-health-alert` son el monitoreo, ver `docs/monitoreo.md`; desde el 21-oct todas envuelven su handler con `withErrorReporting("<nombre>", …)` de `_shared/errorReport.ts`, que guarda excepciones y 5xx en `edge_function_errors` para el aviso por correo: función nueva = mismo wrapper, lo exige `_shared/errorReport.test.ts`): no pasan por `./deploy.sh`; se despliegan a mano desde el árbol principal en `main`, con el mismo candado: `supabase functions deploy <fn> --project-ref nelwgbcddwiaimzbcuas --no-verify-jwt` (todas salvo `send-push`, que verifica JWT: sin la bandera). `supabase/config.toml` fija `verify_jwt` por función con los valores de producción (C-12 de la auditoría: un redeploy sin la bandera dejó el nurture de Starter con 401 del 08 al 18-oct) y `supabase/functions/_shared/verifyJwtConfig.test.ts` lo verifica, porque el CLI ignora en silencio las claves mal escritas. Función nueva = entrada nueva en `config.toml` y en ese test. Migraciones: aplicarlas con `supabase db query --linked -f` + `supabase migration repair --status applied <versión> --linked` (historial compartido con `invest-web`), y dar los grants explícitos: desde el 19-oct una tabla o función nueva en `public` no nace abierta para `anon`/`authenticated` (`docs/esquema-base.md`). **Nunca `supabase config push`** (este `config.toml` no describe Auth, SMTP, hooks ni OAuth y los pisaría). ## Reglas que no son negociables

**Paridad i18n.** Los textos viven en `src/i18n/{es,en,pt,de}.js` (objetos planos `'seccion.sub.campo': "texto"`, 2692 claves por idioma al 19-oct-2026); `translate.js` tiene la traducción pura (fallback a español y luego a la propia clave), `useT.js` el hook que carga el idioma activo con `import()` dinámico y `translations.js` solo agrega los 4 para los pocos consumidores síncronos. Toda clave nueva va en los CUATRO, y `translate.test.js` verifica paridad, variables `{x}`, voseo/exclamaciones y "Sie" por prefijo de fase: al crear un prefijo nuevo, sumarlo ahí. Una clave que falta no rompe el build pero cae al fallback español (ver `useT.js`) — el usuario alemán ve una isla en su UI. Antes de escribir el texto de una clave nueva, ver `../financeos-workspace/branding/voz-de-producto.md` — nunca exclamaciones/emoji de entusiasmo fabricado, nunca personificar la app, y los 4 idiomas tienen que sonar igual de secos entre sí, no solo decir lo mismo.

**Ocultar montos (T13, 08-oct-2026).** `settings.hideAmounts` reemplaza toda cifra de dinero por "•••" (no blur: el número no llega al DOM). Toda cifra NUEVA en pantalla pasa por `<Money>{fmtMoney(x, sym)}</Money>` o, dentro de strings (frases i18n, aria-label, `tickFormatter`), por `useMoney().m(...)` (`components/Money.jsx`). PDFs y Modo Asesor quedan fuera a propósito. El flag es de dispositivo: `exportAllData` lo saca del respaldo/sync y `importAllData` conserva el local (`utils/money.js`).

**Montos con centavos (08-oct-2026).** `fmtMoney` muestra los decimales de la moneda (`config.currencyDecimals`: CLP/COP/PYG… 0, el resto 2, siempre los 2). Nada de `toLocaleString(moneyLocale(), { maximumFractionDigits: 0 })` ni `sym + número` a mano: usar `fmtMoney`/`fmtSignedMoney`/`fmtAmount`, `fmtMoneyCompact` en listas de gráficos, `fmtAxis` en ejes y `currencySymbol(currency, language)` para el símbolo (USD es "$" en inglés, "US$" en el resto; el euro va detrás fuera del inglés: "42,50 €"). `setMoneyLocale(currency, language)` se llama en el render de AppContext/DemoContext. Las calculadoras fiscales por país siguen con `fmtFixed` (enteros) a propósito.

**Demo por idioma (08-oct-2026).** `demoData.js` → `pickDemoPersonaId(lang)`: en → Maya Robinson (EE. UU., USD, `personas/us.js`), de → Aylin Demir (Alemania, EUR, `personas/de.js`), es con región VE (`es-VE`) → Gabriela Rondón (Venezuela, VES con la tasa BCV guardada; ingresos en Bs y en US$ anotados con BCV y paralelo, `personas/ve.js`, desde el 21-oct-2026, EST-5), resto de es/pt → Sofía (COP). `?demo=true&persona=<sofia|us|de|ve>` elige la persona a mano y manda sobre el idioma (enlace del hero de Venezuela en la landing: `https://demo.moyiq.app/app/?demo=true&persona=ve`). Tests en `demoPersona.test.js` (mes bueno positivo, mes difícil negativo, categorías válidas).

**Migraciones de IndexedDB en `src/core/db/migrations.js`** (desde 2026-09-05). `DB_VERSION` ya no es una constante manual — se deriva de `Math.max(...MIGRATIONS.map(m => m.version))`, así que agregar un paso a `MIGRATIONS` bumpea la versión solo. Para cambiar la forma de datos ya guardados (no solo agregar un store), agregar un paso NUEVO al array con `migrate(db, transaction, oldVersion)`: `transaction` cubre todos los stores y sirve para leer/transformar registros existentes (ver el ejemplo de "Data migration during upgrade" en la doc de `idb`). Nunca editar un paso ya shippeado — quien ya pasó por esa versión no la vuelve a correr. `migrations.test.js` prueba el motor con fake-indexeddb, incluyendo que un paso que falla a mitad de camino aborta atómicamente (la base queda en `oldVersion`, sin datos a medio migrar) — correr ese archivo antes de tocar esto. **v5 (09-oct-2026)** unifica "Entretenimiento" → "Entretención" (valor canónico; la etiqueta es "Entretenimiento" en es) en gastos, ingresos, fijos y ajustes, y fusiona presupuestos duplicados SUMANDO límites; foto previa best-effort `pre-category-unify-v5` en `backups`. `importAllData` aplica el mismo mapeo a respaldos/sync viejos (`utils/categoryAliases.js`, tests en `categoryAliases.test.js` y `core/db/categoryUnify.test.js`). Una categoría duplicada nueva se agrega a `CATEGORY_ALIASES` + un paso de migración nuevo.

**Movimientos fijos (08-oct-2026, decisiones de Walter en DECISIONES.md).** Reglas en la store `recurring` (migración v4); las ocurrencias se CALCULAN (`utils/recurring.js`: `occurrencesInMonth`, `monthPlan`), nunca se guardan pendientes. Un registro confirmado lleva `recurringId` + `occurrenceDate` e id determinista `rc-<regla>-<fecha>` (confirmar dos veces no duplica). Suscripciones y Deudas son reglas (`utils/recurringSources.js`, ids `rs-<id>`/`rd-<id>`, `reconcileRecurringSources` al hidratar y tras cada cambio; los registros originales no se tocan). "Te queda" = solo lo real; lo previsto va en "Previsto pendiente". La migración v4 deja una foto previa en la store `backups` (fuera del respaldo/sync; restaurable en Ajustes). Un respaldo/blob sin `recurring` NO vacía las reglas locales. Borrar el registro de una ocurrencia la marca omitida (no la recrea el registro automático); el saldo de una deuda NO se restaura al borrar su gasto, igual que al borrar un pago de "Registrar pago". Si la base existente no abre, `DbOpenError` + pantalla bloqueante (`DbErrorScreen`), nunca fallback silencioso. Tests: `utils/recurring*.test.js`, `core/db/recurring.test.js`.

**Cada cuenta es un espacio separado (18-oct-2026, `core/deviceOwner.js`).** Nada local es "del dispositivo": es de la cuenta activa. IndexedDB: `financeos` para la cuenta que ya la usaba (`fnos_db_legacy_uid`), `financeos__<uid>` para cualquier otra (`db/index.js` resuelve el nombre en cada apertura y reabre si cambió la cuenta). localStorage: toda clave `fos_*`/`fnos_*` es de la cuenta salvo la lista `DEVICE_KEYS` (cotizaciones, error log, demo, el propio estado de cuentas); al cambiar de cuenta se guardan en `fnos_acct__<uid>`, se restauran las de la que entra y se recarga. Cerrar sesión también recarga. Nunca se borra nada de otra cuenta. Una clave local NUEVA de dispositivo va a `DEVICE_KEYS`; si no, viaja con la cuenta (lo correcto por defecto). Datos de antes del cambio sin dueño conocido quedan en `fnos_acct__legacy` y solo los recupera la cuenta cuya licencia Pro coincide en el servidor. Tests: `core/deviceOwner.test.js` (dos cuentas en el mismo navegador). En el servidor (migración `20261018030000`): una licencia = una cuenta (índice único + trigger), y `sync_*`/`save_push_subscription` exigen la sesión de la cuenta dueña (`sync.js` y `push.js` mandan el JWT; sin sesión no hay sync); anon sin privilegios en las tablas de usuario.

**Oferta de Pro: siempre con la prueba de 14 días y la elección anual/mensual (19-oct-2026, auditoría 360 C-03).** `config.pricing` es la fuente única: `trialCheckoutUrl` (mensual) y `trialCheckoutUrlAnnual` son los mismos Payment Links con prueba que la landing; `utils/pricing.js` tiene `checkoutFor(period)`, `annualPerMonth()` y `annualSavingPct()`. Los links sin prueba (…O00 mensual, …O01 anual) ya no se ofrecen desde la app, aunque el webhook los sigue reconociendo, y `pricing.test.js` falla si aparece en `src/` un Payment Link distinto de los dos con prueba. Los Payment Links no limitan una prueba por cliente (`docs/billing-trial-runbook.md`), así que "sin prueba solo para quien ya la usó" necesita un dato del servidor que hoy no existe. ## Supabase

Siete `.sql` en la raíz. **`supabase-e2e-hardening.sql` es la fuente de verdad** de `sync_push`, `sync_pull` y `validate_license`: define `fnos_resolve_hash`, que acepta tanto la clave cruda como el hash de 64 caracteres. `supabase-license-email.sql` y `supabase-license-revoke.sql` también dependen de `fnos_resolve_hash` — **cualquier archivo que toque `licenses` tiene que pasar por esa función**, nunca hashear `p_key` directo con `digest()`.

**Desde el 20-oct-2026 (SEG-12, migración `20261020090000`) lo guardado no es el sha256:** `licenses.key_hash` (y por FK `synced_data`, `push_subscriptions`, `trial_activation_emails`, más `report_email_sends`) guarda `fnos_license_id(x)` = HMAC-SHA256(sha256(CLAVE), pimienta de Vault `license_hash_pepper`). La app no cambió (manda la clave o su sha256); `fnos_resolve_hash` sigue dando la forma "cliente" (la de `user_entitlements.license_key` y su índice único). Las RPC resuelven con `fnos_license_key_id(p_key)`, que re-hashea al vuelo una fila vieja (`key_hash_v` NULL). **Los `.sql` de la raíz quedaron viejos en esto: no volver a correrlos.** La pimienta no se rota ni se borra (sin ella ninguna licencia valida). Prueba: `supabase/tests/license_hash_hmac.sql` (base local).

Ya pasó una vez: volver a correr `supabase-sync.sql` **pisó** esa versión buena y reintrodujo un doble hash (`sha256(sha256(key))`), con lo que `validate_license` aceptaba una licencia que `sync_push` rechazaba con `invalid_license`. Si el sync falla para una licencia que valida bien, es esto. Correr `supabase-e2e-hardening.sql`.

**Antes de "arreglar" un .sql viejo, verificar contra producción.** El 2026-08-22 se encontró `supabase-license-email.sql` desactualizado en el repo respecto de la función real corriendo en Supabase (alguien la había parcheado a mano en el SQL Editor, sin actualizar el archivo). Verificar primero con `supabase db query --linked "select pg_get_functiondef(oid) from pg_proc where proname='...'"` — si production ya está bien, el fix es reescribir el archivo para que coincida, no pisar production con una reconstrucción propia.

`supabase-license-revoke.sql` (2026-08-22): agrega `payment_intent_id` a `licenses` + `revoke_license()`, llamada desde `supabase/functions/stripe-webhook/index.ts` en `charge.refunded`/`charge.dispute.created`. Licencias emitidas antes de esa fecha tienen `payment_intent_id` NULL — un reembolso de una compra vieja no se revoca solo. **`revoke_license()` no borra ninguna fila ni dato personal — solo cambia `status` a `'revoked'`** (verificado con `pg_get_functiondef`, 2026-08-27). El email y la licencia quedan en la base indefinidamente; no hay ningún job de retención/purga. Si en algún momento hace falta borrado real (pedido de un usuario, GDPR), es una decisión de Walter, no algo que se implementó a criterio propio.

**Migraciones nuevas van en `supabase/migrations/`, no como archivo suelto en la raíz** (desde 2026-08-27, ver `supabase/migrations/README.md`). Los 7 `.sql` de la raíz siguen siendo la fuente de verdad del estado histórico — no se tocan. **Desde el 28-oct-2026 (GRANT explícito):** toda tabla o función nueva lleva su `grant` en la misma migración y su fila en `supabase/tests/acl-esperada.json`; `supabase/tests/grants-explicitos.test.js` (en `npm test`) falla si falta, y `node scripts/aclCheck.mjs --catalog <json de supabase/tests/acl_catalog.sql> --matrix supabase/tests/acl-esperada.json` compara la matriz con la base real (solo lectura). Un `grant … to anon` lleva el comentario `-- anon-ok: <motivo>`. Motivo: desde el 30-oct Supabase deja de dar permisos automáticos a las tablas nuevas, ni siquiera a `service_role`.

Destino nuevo = `appLinks.ts` + `deepLink.js` + `vercel.json`; `src/utils/deepLink.test.js` verifica las tres piezas y todos los botones de las plantillas.
- **Service worker cachea agresivamente**. Post-deploy, para verificar cambios: `navigator.serviceWorker.getRegistrations().then(rs => rs.forEach(r => r.unregister()))` + `caches.keys().then(ks => ks.forEach(k => caches.delete(k)))` + hard reload.
- **`~/Documents/.claude/launch.json`** es la config raíz de preview servers (fuera del repo). Si la ruta canónica del repo cambia, ese archivo también.

## Sync en la nube: apagado y con candado

El sync que está en uso es `src/core/sync.js` (por licencia + sesión). **Desde el 20-oct-2026 (C-21 / D-05) tiene frase de paso:** activarlo desde cero crea una frase (PBKDF2-SHA256 600 000 it.; blob `fnos2:`), quien ya sincronizaba con la licencia (v1) sigue igual hasta migrar en Ajustes (respaldo previo, verificación y vuelta a la copia v1 si falla) y puede volver a v1.
